# 星宝色块牌阵技术手册

## 最终目标

把“星宝色块牌阵”做成一个适合 22.5 寸触控桌面屏的亲子轻策略桌面小游戏：孩子移动真实彩色方块，通过语音和触控与星宝互动；屏幕呈现神秘、高级、有流动光幕的星际牌桌；星宝通过屏幕表情、状态动画、语音、光效和桌面区域高亮完成指引与鼓励。

视觉目标以 [目标参考图](references/color_block_target_reference.png) 为第一阶段标准。当前实现基线保存在 [当前基线截图](references/color_block_current_baseline.png)。

## 核心判断

当前单文件 HTML 原型已经能验证布局、语音模拟、回合逻辑和桌面反馈方向，但要接近参考图的美术标准，不能继续依赖纯 CSS 和普通 Canvas 手绘。下一阶段应改为：

- 规则引擎继续使用 `core/color_block_game.py`，保持纯 Python、可测试、不依赖 UI 和硬件。
- 前端从“单 HTML 原型”升级为“资产驱动的浏览器游戏界面”。
- 光幕、粒子、辉光、能量强弱反馈交给 WebGL 2D 渲染层。
- 文字、按钮、设置、语音栏保留 DOM 层，保证清晰、可访问、易适配。
- 星宝形象使用独立角色资产和状态动画，不再只靠 CSS 拼装。

## 推荐技术路线

第一阶段采用 `Python rules + PixiJS/WebGL renderer + DOM HUD`。

选择理由：

- 游戏是 2D 牌桌，不需要完整 3D 场景。
- 参考图的主要难点是流动光幕、粒子、辉光和多层装饰，PixiJS 比纯 Canvas 更适合。
- DOM 更适合中文文本、语音状态、触控按钮、规则弹层和无障碍提示。
- 屏幕已支持触控，第一阶段所有关键操作都应具备可触控路径，不能只依赖键盘或语音模拟输入。
- Python 规则层已经和 UI / 输入层解耦，可以继续复用。

暂不把 Phaser 作为第一选择。Phaser 适合完整 2D 游戏场景、碰撞、地图、角色移动；本游戏更像仪式化牌桌和光效 UI，PixiJS 更轻。若后续加入地图探索、连续动画关卡，再评估 Phaser。

## 前端分层

建议下一阶段把 `web/color_block_game.html` 拆成以下结构：

```text
web/color-block/
  index.html
  src/
    main.js
    game-state.js
    input-controller.js
    voice-controller.js
    touch-controller.js
    feedback-bridge.js
    renderer/
      pixi-stage.js
      light-curtains.js
      card-slots.js
      starfield.js
      xingbao-avatar.js
    ui/
      hud.js
      command-bar.js
      rule-panel.js
      story-panel.js
  assets/
    manifest.json
    backgrounds/
    cards/
    effects/
    xingbao/
    ui/
```

边界原则：

- `game-state.js` 只保存前端镜像状态，不重新发明核心规则。
- `renderer/` 只负责画面、粒子、动画，不决定胜负。
- `input-controller.js` 把语音、触控、快捷键统一成 `play_color_to_lane`、`pass_round`、`ask_hint` 这类意图，其中触控和语音都是正式输入源。
- `feedback-bridge.js` 只接收游戏层生成的高层反馈意图，再映射到星宝状态、光效、语音提示和桌面区域高亮。

## 资产路线

要达到目标图质感，必须建立资产包，而不是所有东西都用 CSS 拼。

第一批资产：

- `backgrounds/star-table.png`：深色星图底板，带细网格、微弱星尘、边框纹理。
- `effects/gold-ribbon-mask.png`、`effects/blue-ribbon-mask.png`：光幕流向贴图或噪声遮罩。
- `cards/card-frame-red.png` 等五色卡框：透明背景，统一尺寸。
- `cards/card-empty-frame.png`：未放置状态。
- `xingbao/listening.png`、`thinking.png`、`happy.png`、`comfort.png`、`point-left.png`、`point-right.png`：星宝状态帧。
- `ui/title-ornament-gold.png`、`ui/title-ornament-blue.png`、`ui/mic-ring.png`：标题和语音栏装饰。

资产规格：

- 目标屏幕按 16:9，优先设计 1920 x 1080。
- 主要 UI 在 1280 x 720、1600 x 900、1920 x 1080 三档验证。
- 透明 UI 资产使用 PNG 或 WebP。
- 角色动画如需要更丝滑，可用 Rive 或 Lottie；先用 PNG 状态帧也可以。
- 资产不能包含儿童隐私信息，不能依赖外部在线加载。

## 22.5 寸桌面布局

星宝应作为屏幕里的主要陪伴角色出现，放在远侧中上方，和桌面中心的实物摆放区形成“星宝看着孩子一起玩”的关系。

布局约束：

- 上中：星宝头像、聆听状态、简短气泡。
- 左上：孩子的“星光线”五格。
- 右下：星宝或对局侧的“守护线”五格。
- 中央：比分、回合、能量汇聚点。
- 底部中：语音入口、触控色块盘、停手确认和提示入口。
- 左下、右下角：星图、故事、规则等低频入口。
- 屏幕中央和实体方块摆放区不要塞满按钮，保持孩子可以看见“放块仪式”。

## 交互路线

第一版交互组合：

- 语音输入：孩子说“红色放星光线”“我要停手”“星宝给我提示”。
- 触控输入：点颜色，再点战线格；或把屏幕色块拖到目标格。
- 实物参与：孩子拿起真实色块，放到桌面对应区域，再用语音或触控确认。
- 星宝反馈：屏幕表情、状态动画、语音文案、光线变化和桌面区域高亮同步。

触控规则：

- 所有可点区域要足够大，适合儿童手指；关键按钮和格子建议不小于 72 px，最低不小于 64 px。
- 点错不惩罚，只温和提示。
- 拖拽时光线要预亮，帮助孩子理解会放到哪条线。
- 长按颜色显示一句简单解释，例如“红色：勇气，直接让这条线变亮”。
- 停手、重开、退出这类高影响操作需要二次轻确认，避免误触。
- 语音和触控状态必须互相同步：触控选中后语音可以继续确认，语音识别后屏幕也要显示可触控修正入口。

## 安全边界

新主线不使用机械臂、舵机、PWM、GPIO 或原始串口控制。小游戏层只产生高层反馈意图：

- 开局：`smile`、欢迎语音、柔和桌面光。
- 思考：`thinking`、聆听动效、低亮度光幕。
- 指路：左/右桌面区域高亮、箭头光效、语音指引。
- 确认：星宝点头状态帧、确认音效、槽位亮起。
- 错误：温和纠错表情、重新提示语音。
- 鼓励：庆祝状态帧、星光粒子、暖色光效。

禁止从小游戏层发送舵机角度、PWM、GPIO、串口原始指令。历史 action 输出如被调用，仍必须经过 `ActionSanitizer`。

## 视觉迭代流程

每次视觉迭代都执行同一套流程：

1. 锁定本轮目标，例如“提升光幕密度和标题装饰”。
2. 修改前端或资产。
3. 截图至少两档：`1600 x 900` 和 `1280 x 720`。最终验收加 `1920 x 1080`。
4. 把新截图与 [目标参考图](references/color_block_target_reference.png) 并排观察。
5. 输出差异报告，使用 `docs/COLOR_BLOCK_VISUAL_GAP_REPORT_000.md` 的格式。
6. 只选择 3 到 5 个最高影响问题进入下一轮，避免每轮同时改散。

评分维度：

- 构图还原度：左右牌阵、中央比分、星宝、语音栏是否形成同样的舞台关系。
- 光幕表现：是否有流动层次、粒子密度、强弱变化、能量汇聚。
- 标题和装饰：字体、星徽、细线、边框是否足够精致。
- 卡牌质感：卡框、内纹、发光、放置状态是否像可收集物。
- 星宝角色：是否足够 Q 版、可爱、神秘，状态动作是否明显。
- 交互可读性：孩子能否一眼知道该说什么、点哪里、放哪里。
- 适配稳定性：不同尺寸无重叠、无滚动、无文字溢出。

目标分数：

- 原型可演示：总分 70/100。
- 第一阶段可给孩子试玩：总分 82/100，所有核心维度不低于 3.5/5。
- 接近目标图标准：总分 90/100，光幕、标题、卡牌、星宝四项不低于 4.3/5。

## 测试策略

规则层：

- 继续测试回合胜负、三局两胜、停手、颜色效果、星宝策略。
- 新规则必须先写测试，再接 UI。

前端层：

- 截图验证三档屏幕尺寸。
- 验证无滚动条、无文字溢出、按钮不遮挡牌桌。
- 验证语音输入、触控点选、拖拽放置、长按说明、二次确认和停手。
- 验证弱线增强时光幕亮度变化。

历史兼容层：

- 无串口时必须完整可玩。
- 新主线不要求串口或机械臂存在。
- 如果维护旧串口能力，只发送白名单动作，非法动作回退到安全默认值。
