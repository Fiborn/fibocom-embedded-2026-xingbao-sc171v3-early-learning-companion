# 星宝与触控游戏协同交付包

这份文件是给同学的交付包目录。你可以先把本文档发给负责游戏、机械臂动作和星宝表情的同学，再按下面顺序附上其他文档。

## 交付目标

我们要把“触控游戏”和“星宝语音陪伴”拆成两个清晰模块：

- 游戏负责规则、状态、分数、关卡、触控结果。
- 星宝负责听懂孩子的话、归类意图、组织儿童友好的语音反馈。
- 机械臂、表情、灯效只接收高层动作名，不接收舵机角度、PWM、GPIO 或串口原始命令。

第一版先跑通最小闭环：

```text
孩子说“我不会”
-> 星宝识别为 get_hint
-> 游戏返回当前提示
-> 星宝把提示说给孩子听
```

## 建议阅读顺序

### 1. 协同规则

文件：

```text
docs/GAME_XINGBAO_COLLAB_RULES.md
```

用途：

- 明确星宝和游戏各自负责什么。
- 明确哪些事情不能做。
- 明确触控游戏里语音应该作为辅助通道，而不是替代触控操作。

### 2. 接口规范

文件：

```text
docs/GAME_XINGBAO_API_SPEC.md
```

用途：

- 定义星宝发给游戏的 `game_command`。
- 定义游戏返回给星宝的 `game_response`。
- 定义游戏主动通知星宝的 `game_event`。
- 给出 Python / JavaScript 的推荐函数形态。

### 3. 意图表

文件：

```text
docs/GAME_INTENTS_V0.md
```

用途：

- 给出第一版固定 `intent`。
- 说明孩子可能怎么说。
- 说明游戏需要返回什么。

同学需要基于颜色、图形、记忆三个游戏，补充和修订这张表。

### 4. 游戏状态模板

文件：

```text
docs/GAME_STATE_TEMPLATE.md
```

用途：

- 让同学说明每个游戏有哪些状态字段。
- 让同学说明每个游戏会主动发哪些事件。
- 让星宝侧后续能稳定读取游戏状态，而不是靠猜。

### 5. 动作与表情交付说明

文件：

```text
docs/ACTION_EXPRESSION_HANDOFF.md
```

用途：

- 整理当前允许输出的机械臂高层动作。
- 整理当前允许输出的星宝屏幕表情。
- 整理当前允许输出的灯效。
- 让同学判断哪些能实现、哪些不能实现、哪些有安全风险。

### 6. 动作与表情可行性回填模板

文件：

```text
docs/ACTION_EXPRESSION_FEASIBILITY_TEMPLATE.md
```

用途：

- 这是给同学填写并返回的模板。
- 同学需要把机械臂动作、星宝表情、灯效的可实现性写清楚。
- 如果某个动作不能做，要写替代方案。

### 7. 可直接发送给同学的话术

文件：

```text
docs/MESSAGE_TO_GAME_DEV.md
```

用途：

- 可以直接复制发给同学。
- 里面已经包含任务背景、他需要实现什么、需要返回什么。

## 同学需要交回什么

请同学至少交回以下内容：

- 三个游戏分别支持哪些 `intent`。
- 每个 `intent` 对游戏状态有什么影响。
- 每个 `intent` 返回的 `message` 应该怎么写。
- 每个游戏当前有哪些状态字段。
- 游戏会主动发哪些 `game_event`。
- 哪些机械臂动作可以实现，哪些不能实现。
- 哪些星宝表情资源已经有，哪些需要补。
- 哪些灯效可以实现，哪些需要替代。
- 对当前动作、表情、灯效白名单的新增或删除建议。

## 对同学的重点嘱托

请不要让游戏接大模型，也不要让游戏理解孩子自由说话。游戏只处理固定 `intent`，并返回结构化数据。

请不要让星宝侧直接控制机械臂底层硬件。星宝只会输出类似 `nod`、`smile`、`warm_breath` 这样的高层名字。

如果某个动作看起来能做，但不适合儿童近距离桌面场景，请直接标记为高风险，并给出屏幕表情或灯效替代方案。

第一阶段我们追求稳定闭环，不追求动作数量多。每个动作都要安全、清楚、孩子能理解。
