# 星宝游戏语音、读题、缓存与状态机专项检查报告

检查日期：2026-07-23  
检查范围：中央控制程序、游戏语音桥、板端触控游戏发布包、启动脚本、缓存目录、自动化测试。  
保护范围：未修改 `pc5.py`，未向板端写入任何文件。

## 一、结论摘要

当前“进入游戏没有欢迎语、题目不播报、读题按钮无声、页面和状态机不同步”不是一个单点故障，而是四个问题叠加：

1. 旧版演示补丁默认关闭全部游戏自身语音。`XINGBAO_DEMO_DISABLE_GAME_SPEECH` 的默认值为 `"1"`，`speak()` 只有在该开关关闭时才会发 `speech_request`。欢迎语、自动读题、手动“读题”共用这条路径，因此会一起消失。
2. 中央视角和游戏视角同时具备播报能力，但没有明确唯一播报责任。旧补丁为避免“游戏题目语音 + 中央固定反馈语音”重复播放，采用了全局静音，结果把必须保留的题目和读题也关掉了。
3. 语音协议只确认“已排队”，不确认“已开始/已播完”。游戏反馈页固定约 1.15 秒后进入下一题，不等待 TTS 完成，页面、当前题目和扬声器内容必然可能错位。
4. 预缓存目前不是启动保障。项目提供了手工 `--prepare-demo-tts-cache` 命令，但启动脚本不执行，也不检查缓存完整性。本机 `work/cache` 中没有任何 `demo_*.wav`。

综合评级：游戏核心逻辑仍在，但游戏语音链路和状态同步不完整，属于 P0 可用性问题；缓存与可观测性属于 P1 稳定性问题。

## 二、已确认的问题

### P0-1：旧演示补丁默认全局关闭游戏语音

证据：

- `tmp_touch_game_patch_test_20260704/xingbao_touch_game/src/app.py` 中，`XINGBAO_DEMO_DISABLE_GAME_SPEECH` 默认值为 `"1"`。
- 同文件的 `speak()` 只有在 `not self.demo_disable_game_speech` 时才调用 `on_speech_request`。
- 游戏初始化欢迎语、难度页提示、`start_game()` 自动题目、`read_current_question()` 手动读题、答题反馈都调用同一个 `speak()`。

影响：

- 欢迎语消失。
- 进入题目后不自动读题。
- 点击“读题”按钮只改页面文字/日志，不向中央 TTS 发请求。
- 答对、答错、提示、总结等游戏内部语音都可能消失。

根因判断：为规避重复播报而采用了过大的总开关，关闭粒度错误。

### P0-2：页面状态机不等待语音完成

证据：

- `core/game_speech_server.py` 收到有效请求后立即返回 `queued`。
- UI 侧 `CentralSpeechClient` 收到 `queued` 后即结束该请求，没有接收后续 `started` 或 `finished`。
- 游戏 `GAME_FEEDBACK` 状态只依赖本地 `feedback_remaining`；约 1.15 秒归零后直接切回 `GAME_RUNNING` 并播下一题。
- 实际 TTS 合成与播放时间可能明显超过 1.15 秒。

影响：

- 页面已经显示下一题，扬声器还在播放上一题反馈。
- 下一题语音进入队列后可能晚于页面数秒播放。
- 孩子看到的题目、语音听到的题目、语音查询返回的 `current_goal` 可能不是同一轮。

根因判断：状态机只以墙钟定时推进，语音链路没有完成事件，两个子系统不存在同步点。

### P0-3：游戏状态 API 缺少 UI 页面状态

证据：

- 游戏侧 `get_game_state()` 返回题目、轮次、分数等数据，但没有返回 `AppState` 对应的 `HOME / DIFFICULTY_SELECT / GAME_RUNNING / GAME_FEEDBACK / GAME_SUMMARY`。
- `GAME_FEEDBACK` 期间，游戏对象可能已经生成下一题，而页面仍显示上一题的反馈层。
- 中央侧因此无法判断当前应该复述“反馈内容”还是“下一题内容”。

影响：

- 中央语音查询与屏幕页面语义不一致。
- `repeat_prompt`、`get_goal`、欢迎/反馈播报可能引用错误阶段的数据。
- 无法对“页面状态 == 后端状态”做自动验收。

根因判断：数据状态和呈现状态分开维护，但协议没有携带呈现状态与题目版本号。

### P0-4：欢迎语触发点不稳定

证据：

- 游戏对象首次创建时会调用一次首页 `speak()`。
- 随后 `activate_display()` 又会把状态重置为 `HOME`，但只重置 `message`，不会再次调用 `speak()`。
- 游戏对象被复用时，重新进入游戏只调用 `activate_display()`，因此第二次及以后进入游戏中心没有新的欢迎播报。
- 桌面点击“游戏”还会先发送“游戏，打开小游戏”的点读语音，可能与游戏首页提示竞争队列。

影响：

- 首次进入是否听到欢迎语依赖对象创建时机和中央服务是否已就绪。
- 第二次进入通常没有游戏中心欢迎语。
- 桌面点读和游戏欢迎可能顺序混乱。

根因判断：欢迎语绑定在构造函数，而不是绑定在“页面真正进入并显示”的生命周期事件。

### P1-1：预缓存没有自动准备、没有完整性检查

证据：

- `main.py` 仅在显式传入 `--prepare-demo-tts-cache` 时生成缓存，然后立即退出。
- `deploy/board_start_demo.sh`、`deploy/board_start_runtime.sh`、`deploy/board_start_full_demo.sh` 均未执行缓存准备或缓存检查。
- 本机 `work/cache` 没有任何 `demo_*.wav`。
- `_speak_with_demo_cache()` 只有在文件已存在且大于 1000 字节时才命中，否则临时调用云 TTS。

影响：

- 无网络、API Key 异常、首次合成慢时，游戏表现为长时间无声。
- 发布包不能证明固定提示音已经准备好。
- 重启后没有清晰的“缓存就绪/缺失”状态。

根因判断：缓存能力只做成维护命令，没有纳入发布和启动生命周期。

### P1-2：缓存覆盖范围不足

现有固定缓存主要覆盖：

- 少量桌面固定文案。
- 进入游戏、选择难度。
- 少量形状题目。
- 固定答对、答错、姿势提醒。

未完整覆盖：

- 游戏中心首页欢迎和难度选择原文。
- 颜色游戏全部颜色题目。
- 数数游戏各数字题目。
- 英语题库。
- 本领挑战题库。
- 记忆游戏阶段提示。
- 每局总结和动态分数文案。

影响：即使执行现有缓存命令，大部分游戏题目仍依赖临时云合成。

### P1-3：语音请求失败后只打印日志，UI 没有可见降级状态

证据：

- `CentralSpeechClient` 后台线程连接失败时只打印 `[game-speech] central unavailable`。
- 请求没有重试、离线队列、失败回调或 UI 提示。
- 游戏 `speak()` 在发送前就把文字写进页面，因此“屏幕有字、实际无声”不会被状态机识别为失败。

影响：

- 用户只看到无声，无法判断是中央服务、网络、TTS、播放器还是缓存问题。
- 自动化测试不能从 UI 状态发现语音失败。

### P1-4：重复播报治理方式不完整

当前存在两类消息：

- 游戏直接发 `speech_request`：适合欢迎、题目、读题、游戏内动态反馈。
- 游戏发 `game_event`，中央再生成固定 TTS：适合跨模块编排和动作反馈。

如果两者同时用于同一阶段，会重复播报；如果用总开关关闭第一类，题目和读题又会消失。缺少按 `speech_role`、`utterance_id`、`question_id` 去重和明确归属。

## 三、现有测试与质量基线

执行环境：项目 `.venv`，Python 3.12。

- `python -m compileall .`：通过。
- `pytest -q`：207 项中 191 通过、16 失败。
- 本次最相关的 `tests/test_game_speech_server.py` 与读题中断测试：4 项通过。

现有相关测试的覆盖缺口：

- 只验证请求进入队列，没有验证真实生命周期 `queued -> started -> finished/failed`。
- 没有验证进入游戏一定产生一次欢迎语。
- 没有验证每次新题产生一次且仅一次自动读题。
- 没有验证“读题”按钮在旧演示模式下仍能发声。
- 没有验证页面状态和语音对应同一 `question_id`。
- 没有验证缓存清单在启动前完整。
- 没有验证中央离线时的重试和 UI 降级。

其余 16 个失败说明当前工作树还存在既有回归，包括语音事件顺序、实时 TTS 文本前缀、预置知识短路、CLI 参数测试和配置期望等。本次修复必须避免把这些既有失败误算为新回归，并优先消除与游戏语音直接相关的新增失败。

## 五、推荐修复方向

推荐采用“单一播报责任 + 语音完成回执 + 页面版本绑定”的方案：

1. 欢迎、题目、手动读题由游戏 UI 生成并发 `speech_request`。
2. `game_event` 只用于状态、表情、灯光和机械臂等编排；同一事件不再额外生成重复题目 TTS。
3. 每条语音携带 `utterance_id`、`page_state`、`game_id`、`question_id`、`speech_role`。
4. 中央语音服务提供 `queued / started / finished / failed / interrupted` 完整状态。
5. 游戏状态机在关键阶段等待对应语音 `finished`，同时保留安全超时，避免 TTS 故障卡死游戏。
6. 缓存改为清单驱动：发布时生成，启动时只做快速完整性校验；缺失时后台补齐，失败时保留文字与本地降级提示。
7. 去掉默认全局静音，改成按 `speech_role` 去重；“读题”始终允许发声。

## 六、验收标准

- 每次进入游戏中心，欢迎语恰好播放一次。
- 选择难度后，开始提示与第一题按顺序播放，不重复、不丢失。
- 每道新题自动读题一次。
- 点击“读题”可立即重播当前题，且不会播到上一题或下一题。
- 反馈页在反馈语音完成前不切换到下一题；TTS 失败时在设定超时后安全继续。
- 屏幕、状态 API、正在播放的语音具有相同 `game_id + question_id + page_state`。
- 固定提示缓存清单可检查，发布包能报告命中、缺失和损坏数量。
- 中央离线时 UI 显示“语音暂不可用”，但触控游戏继续工作。
- 相关专项测试全部通过；全量测试不新增失败。
